= modern-gitops-stack-module-jupyterhub
// Document attributes to replace along the document

A https://modern-gitops-stack.io[Modern GitOps Stack] module to deploy https://jupyter.org/hub[JupyterHub] on Kubernetes.

== Spawner profiles

The user pod form is driven by KubeSpawner `profile_list`, so a user picks the resources for the server before it starts (the same idea as the Kubeflow notebook form). Three options are offered:

[cols="1,2,2",options="autowidth,header"]
|===
|Option |Choices |Notes
|CPU |`1 vCPU` (default) plus a free-form field |Any positive number of vCPU, e.g. `0.5`, `2`, `3.5`
|Memory |`2 GB` (default) plus a free-form field |Any positive integer of GB, e.g. `4`, `8`, `16`
|GPU |`Sem GPU` (default), `1 GPU`, `2 GPUs` plus a free-form field |Requests the `nvidia.com/gpu` extended resource
|===

The GPU choices only request the extended resource. Clusters that advertise `nvidia.com/gpu` normally taint those nodes, so set `gpu_scheduling` with the `node_selector` and `tolerations` your GPU nodes require; the module applies them to the GPU choices only, never to the CPU-only ones.

[source,hcl]
----
module "jupyterhub" {
  # ...
  gpu_scheduling = {
    node_selector = { "nvidia.com/gpu.present" = "true" }
    tolerations = [
      {
        key      = "nvidia.com/gpu"
        operator = "Exists"
        effect   = "NoSchedule"
      },
    ]
  }
}
----

NOTE: `Sem GPU` is the default so the module works on clusters without the NVIDIA device plugin (such as kind). Selecting a GPU on such a cluster leaves the pod `Pending` until the plugin and a GPU node exist — that is intentional, because it surfaces the missing capacity instead of silently starting a CPU-only server.
